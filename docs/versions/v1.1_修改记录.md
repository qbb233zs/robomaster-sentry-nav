# v1.1 修改记录

> 基线版本：`v1.0`  
> 本版版本：`v1.1`  
> 路径基准：压缩包根目录 `nav-master-ccut-WCZ-newcccutNav2/`  
> 比对口径：比较解压后的源码快照，排除 `build/`、`install/`、`log/`、`__pycache__/`、`*.pyc` 和手工 `.bak` 备份。导航包内以逐文件 diff 为准；串口工程不在导航压缩包内，另按修改时间和备份文件核对版本时间窗。本文既记录本版真实差异，也说明 1.0 基线之前已经存在的前置修复。

## 1. 本版结论

导航压缩包内，本版只修改了 `fake_vel_transform` 的速度坐标转换链，共 2 个业务源码文件：

1. `fake_vel_transform.hpp`
2. `fake_vel_transform.cpp`

核心变化是：新增 TF 监听，实时读取 `odom -> base_footprint` 的底盘 yaw，并尝试用它把 Nav2 输出的速度旋转到真实底盘坐标系，而不是只使用里程计中的 yaw。

同一时间窗内，导航工程之外的 `CCUTVision/rm_serial_driver` 还修改了 3 个文件，加入 `cmd_vel_yaw_offset_deg: 90.0` 的速度坐标旋转。该串口修改发生在 1.0 打包之后、1.1 打包之前，因此归入本版时间窗，详见第 5 节。

需要注意：**v1.1 是中间方案，不是最终方案**。v2.0 已经把速度旋转重新改回 `current_robot_base_angle_`，并明确由电控板处理 `gimbal -> chassis` 的变换。因此阅读 v1.1 时，应把它理解为一次“直接使用底盘角”的尝试，而不是当前最终架构。

## 2. 本版要解决的问题

v1.0 中，`fake_vel_transform.cpp` 把 Nav2 速度旋转到输出坐标系时，只使用：

```cpp
const double yaw_diff = current_robot_base_angle_;
```

而 `current_robot_base_angle_` 来自：

```cpp
current_robot_base_angle_ = tf2::getYaw(msg->pose.pose.orientation);
```

也就是说，v1.0 只有里程计姿态这一个角度来源。代码期望 Nav2 的速度最终能被真实底盘正确执行，但当云台/雷达相关坐标系与真实底盘 `base_footprint` 存在相对转角时，只用里程计中的 yaw 做平移分量旋转，不能直接得到真实底盘需要的平移方向。

v1.1 的处理方式是：

- 增加 TF Buffer 和 TransformListener；
- 增加 `odom_frame`、`chassis_frame` 参数；
- 查询 `odom -> base_footprint`；
- 从 `base_footprint` 的四元数中取 yaw；
- 优先用这个底盘 yaw 执行速度旋转。

#### 4.2.4 新增底盘 yaw 查询函数

完整实现：

```cpp
void FakeVelTransform::updateChassisAngle()
{
  try {
    const auto tf_stamped = tf_buffer_->lookupTransform(
      odom_frame_, chassis_frame_, tf2::TimePointZero);
    current_chassis_angle_ = tf2::getYaw(tf_stamped.transform.rotation);
    has_chassis_angle_ = true;
  } catch (const tf2::TransformException & ex) {
    RCLCPP_WARN_THROTTLE(
      get_logger(), *get_clock(), 5000, "chassis TF %s -> %s unavailable: %s",
      odom_frame_.c_str(), chassis_frame_.c_str(), ex.what());
  }
}
```

关键点：

- `lookupTransform(odom_frame_, chassis_frame_, tf2::TimePointZero)` 查询 `odom -> base_footprint`；
- `tf2::TimePointZero` 表示取 Buffer 中当前可获得的最新变换；
- 成功一次后，`has_chassis_angle_` 变为 `true`；
- TF 查询失败时不会抛出到回调外，只做 5 秒限频告警。

#### 4.2.5 在里程计回调中刷新底盘角

修改前：

```cpp
if ((rclcpp::Clock().now() - last_controller_activate_time_).seconds() > CONTROLLER_TIMEOUT) {
  current_robot_base_angle_ = tf2::getYaw(msg->pose.pose.orientation);
}
```

修改后：

```cpp
if ((rclcpp::Clock().now() - last_controller_activate_time_).seconds() > CONTROLLER_TIMEOUT) {
  current_robot_base_angle_ = tf2::getYaw(msg->pose.pose.orientation);
  updateChassisAngle();
}
```

#### 4.2.6 无同步速度路径改用底盘角

`cmdVelCallback()` 中，无法与 local plan 同步时原本直接发布速度。v1.1 的改动为：

修改前：

```cpp
auto aft_tf_vel = transformVelocity(msg, current_robot_base_angle_);
```

修改后：

```cpp
const double yaw_diff =
  has_chassis_angle_ ? current_chassis_angle_ : current_robot_base_angle_;
auto aft_tf_vel = transformVelocity(msg, yaw_diff);
```

含义：只要曾经成功取得过底盘角，就优先用 `odom -> base_footprint` 的 yaw；没有取得过时才退回里程计 yaw。

#### 4.2.7 同步速度路径也改用底盘角

`syncCallback()` 修改前：

```cpp
float yaw_diff = current_robot_base_angle_;
```

修改后：

```cpp
updateChassisAngle();
// The command is expressed in the world-stable fake base frame. Rotate it into the real
// chassis frame using odom -> base_footprint directly, without going through gimbal_yaw.
const double yaw_diff =
  has_chassis_angle_ ? current_chassis_angle_ : current_robot_base_angle_;
```

这里的注释直接说明了本版设计意图：把速度旋转到真实底盘坐标系，不再经由 `gimbal_yaw`。

### 5.5 `sendDataTwist()` 发串口帧前旋转平移速度

修改前：

```cpp
const bool finite =
    std::isfinite(msg->linear.x) && std::isfinite(msg->linear.y) && std::isfinite(msg->angular.z);
packet.linear_x = finite ? static_cast<float>(msg->linear.x) : 0.0f;
packet.linear_y = finite ? static_cast<float>(msg->linear.y) : 0.0f;
packet.angular_z = finite ? static_cast<float>(msg->angular.z) : 0.0f;
```

修改后：

```cpp
const bool finite =
    std::isfinite(msg->linear.x) && std::isfinite(msg->linear.y) && std::isfinite(msg->angular.z);
const double vx = finite ? msg->linear.x : 0.0;
const double vy = finite ? msg->linear.y : 0.0;
const double c = std::cos(cmd_vel_yaw_offset_rad_);
const double s = std::sin(cmd_vel_yaw_offset_rad_);
packet.linear_x = static_cast<float>(vx * c - vy * s);
packet.linear_y = static_cast<float>(vx * s + vy * c);
packet.angular_z = finite ? static_cast<float>(msg->angular.z) : 0.0f;
```

当参数为 `90.0°` 时：

```text
cos(90°) = 0
sin(90°) = 1

packet.linear_x = -vy
packet.linear_y =  vx
```

也就是把 ROS 常见的“x 向前、y 向左”转换成电控板使用的“x 向右、y 向前”。`angular.z` 没有旋转，只做 NaN/Inf 熔断。

本次串口改动没有修改 `timestamp_offset_`，也没有修改串口帧格式、CRC、收发线程或看门狗；它只是在 `sendDataTwist()` 发帧前增加平移速度旋转。

### 5.6 这一改动与 v1.1 导航代码的关系

同一个 `1.0 → 1.1` 时间窗里，导航侧尝试使用 `odom -> base_footprint` 底盘角，串口侧则增加固定的 90° 坐标旋转。两者一个在导航速度转换层，一个在串口发送层。

v2.0 后来取消了导航侧对 `current_chassis_angle_` 的优先使用，但串口侧的 90° 偏移保留下来；因此看方向链时必须把这两个层次分开：

```text
Nav2 速度
  -> fake_vel_transform（导航侧角度处理）
  -> /cmd_vel
  -> rm_serial_driver::sendDataTwist（串口侧 90° 旋转）
  -> 电控板
```

### 6.1 翻译官 `pointcloud_to_laserscan` 的 tf2 死锁修复

文件路径：

```text
nav-master-ccut/src/rm_perception/pointcloud_to_laserscan/src/pointcloud_to_laserscan_node.cpp
```

该文件在 1.0、1.1、2.0、2.1、3.0、3.1 六个快照中的 SHA-256 都是：

```text
d86ba9d70b8aa12c10b7403b91294a6028e19c988dd4226e7a9b91a494d2ed85
```

修复时间：2026-10-13 19:23:13，早于 1.0 打包时间 2026-10-17 12:56。

#### 问题现象

建图/导航时 `/red_standard_robot1/obstacle_scan` 偶发 0 Hz，`/map` 随后冻结。上游 `terrain_ext` 仍正常，但翻译官不再输出。

#### 根因

ROS Humble 的 `tf2_ros 0.25.23` 中，`MessageFilter` 的 futures 等待路径可能与 `TransformListener` 线程发生 AB-BA 死锁：

```text
主线程持有 timer_to_request_map_mutex_，等待 transformable_requests_mutex_
TF 线程持有 transformable_requests_mutex_，等待 timer_to_request_map_mutex_
```

两把锁互等后，翻译官静默卡死。

#### 修改一：不再让 MessageFilter 驱动回调

修改前：

```cpp
message_filter_ = std::make_unique<MessageFilter>(
  sub_, *tf2_, target_frame_, input_queue_size_,
  this->get_node_logging_interface(),
  this->get_node_clock_interface());
message_filter_->registerCallback(
  std::bind(&PointCloudToLaserScanNode::cloudCallback, this, _1));
```

修改后：

```cpp
// 直接在点云回调里做 TF 转换，绕过 MessageFilter 的 futures 等待路径。
sub_.registerCallback(
  std::bind(&PointCloudToLaserScanNode::cloudCallback, this, _1));
```

#### 修改二：精确时间戳 TF 不可用时，允许使用 0.25 秒内的最新 TF

修改后（关键代码节选，保留原来的异常处理分支）：

```cpp
auto cloud = std::make_shared<sensor_msgs::msg::PointCloud2>();
bool transformed = false;
try {
  tf2_->transform(*cloud_msg, *cloud, target_frame_, tf2::durationFromSec(tolerance_));
  transformed = true;
} catch (tf2::TransformException & ex) {
  try {
    const auto tf_latest = tf2_->lookupTransform(
      target_frame_, cloud_msg->header.frame_id, tf2::TimePointZero);
    const double tf_age_sec =
      (rclcpp::Time(cloud_msg->header.stamp) -
      rclcpp::Time(tf_latest.header.stamp)).seconds();
    if (tf_age_sec > -0.25 && tf_age_sec < 0.25) {
      tf2::doTransform(*cloud_msg, *cloud, tf_latest);
      transformed = true;
      RCLCPP_WARN_THROTTLE(
        this->get_logger(), *this->get_clock(), 5000,
        "Transform at cloud stamp unavailable (%s); used latest transform (%.0f ms old)",
        ex.what(), tf_age_sec * 1000.0);
    }
  } catch (tf2::TransformException & fallback_ex) {
    RCLCPP_ERROR_STREAM(this->get_logger(), "Transform failure: " << fallback_ex.what());
    return;
  }
}
if (!transformed) {
  return;
}
cloud_msg = cloud;
```

这段既包含翻译官逻辑修复，也包含时间戳兜底：点云时间戳对应的 TF 还没到，可以用最近 TF，但 TF 年龄必须小于 `0.25 s`，否则丢帧。

### 6.2 small-GICP 的 `map -> odom` 时间戳修复

文件路径：

```text
nav-master-ccut/src/rm_localization/small_gicp_relocalization/src/small_gicp_relocalization.cpp
```

文件修改时间：2026-09-22 06:55:25，早于 1.0。

修改前：

```cpp
transform_stamped.header.stamp = last_scan_time_;
```

修改后：

```cpp
transform_stamped.header.stamp = this->now();
```

旧逻辑使用上一帧点云的 `last_scan_time_` 给 `map -> odom` 打戳。点云时间戳一旦变旧或冻结，`map -> odom -> ... -> gimbal_yaw_fake` 整条 TF 链会被 tf2 解析到旧时刻，全局代价地图中的机器人位姿不再更新，规划器会一直从旧位置规划。

注意：这是 1.0 之前已有的修复；2.1 改的是 GICP 的发布线程和 `result_t_` 锁，不是重新修改这一行打戳代码。

## 7. 修改后的运行链

```text
Nav2
  -> /cmd_vel
  -> fake_vel_transform::cmdVelCallback()
       | 若不能与 local_plan 同步：立即转换并发布
       | 若能同步：保存为 latest_cmd_vel_
  -> odom/local_plan ApproximateTime 同步
  -> fake_vel_transform::syncCallback()
  -> odom -> base_footprint TF
  -> current_chassis_angle_
  -> transformVelocity()
  -> 输出速度
```

速度旋转公式本身没有改变，仍然是：

```cpp
aft_tf_vel.linear.x = twist->linear.x * cos(yaw_diff) + twist->linear.y * sin(yaw_diff);
aft_tf_vel.linear.y = -twist->linear.x * sin(yaw_diff) + twist->linear.y * cos(yaw_diff);
```

本版改变的只是 `yaw_diff` 的来源。

## 8. 行为影响和版本边界

### 8.1 对导航的影响

- 平移速度的旋转角从“里程计 yaw”切换为“`odom -> base_footprint` 的 yaw”；
- 当底盘 TF 能正常发布时，速度会按照真实底盘角转换；
- 在从未成功取得过底盘角时，会退回原来的里程计 yaw，不会因为查询失败直接停止节点；
- 首次成功后如果后续 TF 中断，`has_chassis_angle_` 不会自动清零，本版会继续使用最后一次缓存到的底盘角。这是 v1.1 中间方案的边界，v2.0 已不再用这个角做最终速度旋转。

### 8.2 版本范围说明

在 5 个 QY 导航压缩包范围内，本记录未列出的模块都没有源码差异，保持 v1.0 原样；串口工程按第 5 节单独归档。翻译官和 small-GICP 的时间戳修复属于 1.0 之前的基线，不是本版新增。
